# 어드민·백엔드 통계 MVP 기획

- 상태: 개발 기준안
- 작성일: 2026-08-20
- 대상: Pakit 런칭 전 운영 도구
- 범위: 전체 결과 관리와 백엔드가 직접 확인할 수 있는 통계

## 1. 목표

런칭 직후 운영자가 다음 질문에 빠르게 답할 수 있는 최소 어드민을 만든다.

1. 실제로 생성된 테스트 결과는 몇 개인가?
2. 특정 `result_code`의 사용자가 어떤 결과를 받았는가?
3. 어떤 MBTI·장난감·키워드·성향이 많이 나오는가?
4. 결과를 만든 사용자 중 실제 궁합 계산까지 완료한 결과는 얼마나 되는가?
5. 어떤 MBTI 조합의 궁합이 많이 계산되고 평균 점수는 어떠한가?

어드민은 초기에는 **읽기 전용**으로 제공한다. 결과 문구 수정, 점수 변경, 원본 답변 조회,
결과 삭제는 이번 범위에 포함하지 않는다.

## 2. GA와 백엔드 어드민의 경계

프론트 행동 분석은 Google Analytics에서 담당한다. 백엔드는 자신이 확실히 관측할 수 있는
서버 데이터만 관리한다.

### GA에서 확인할 항목

- 테스트 시작 버튼 클릭
- 문항별 진입과 이탈
- 테스트 완료 화면 도달
- 궁합 CTA 클릭
- 공유 버튼 클릭
- 공유 링크 유입
- UTM source·medium·campaign
- 페이지뷰와 프론트 전환 퍼널

### 백엔드 어드민에서 확인할 항목

- 정상 저장된 테스트 결과
- 공개 결과 조회 API의 성공 요청
- 궁합 API가 정상 계산한 결과
- 저장된 결과의 MBTI·장난감·키워드·성향·버전 분포
- 성공한 궁합의 참여 결과 코드, MBTI 조합, 점수와 계산 버전

따라서 백엔드 어드민에서는 테스트 시작 수, 시작 대비 완료율, CTA 클릭률, 공유율, UTM별
전환율을 제공하지 않는다. 이 수치를 백엔드 결과 수와 임의로 섞어 하나의 전환율로 만들지 않는다.

## 3. 현재 가능한 통계와 추가 저장이 필요한 통계

### 기존 `assessment_results`만으로 가능한 것

- 오늘·최근 7일·최근 30일·누적 결과 수
- 일별 결과 생성 추이
- 결과 코드와 닉네임 검색
- MBTI 분포
- 장난감과 최종 결과명 분포
- 상단 키워드 24종 분포
- 네 성향 축의 평균·중앙값·구간 분포
- 문항 버전·콘텐츠 버전별 결과 수
- 개별 결과의 생성 시점 전체 스냅샷

MBTI는 새 결과 스냅샷의 `compatibility_profile.mbti`에서 읽는다. 해당 필드가 없는 기존 결과는
목록과 통계에서 `알 수 없음`으로 구분하며 캐릭터 이름으로 MBTI를 임의 역추론하지 않는다.

### 백엔드 사용 기록을 추가해야 가능한 것

- 결과 조회 API 호출 수
- 한 번 이상 다시 조회된 고유 결과 수
- 궁합 계산 완료 횟수
- 궁합을 한 번 이상 사용한 고유 `mine_result_code` 수
- 테스트 결과 중 궁합을 경험한 결과의 비율
- 결과 코드당 평균 궁합 계산 횟수
- 자주 계산된 MBTI 조합
- 궁합 점수 평균과 구간 분포

현재는 결과 조회와 궁합 계산 성공 기록을 저장하지 않으므로 위 수치는 계측 기능 배포 이후부터
제공한다. 과거 API 호출은 소급 복원하지 않는다.

계측 시작 시각은 운영 설정 `PAKIT_USAGE_TRACKING_STARTED_AT`에 ISO 8601 형식으로 기록한다.
궁합 경험 비율처럼 전체 결과 수를 분모로 쓰는 지표는 이 시각 이후 생성된 결과만 포함한다.

- 최근 30일 생성 결과 수
- 누적 생성 결과 수
- 오늘 성공한 궁합 계산 수

- 일별 결과 생성 수
- 일별 공개 결과 조회 수
- 일별 궁합 계산 완료 수

#### 빠른 분포

- MBTI 상위 5개
- 장난감 상위 5개
- 상단 키워드 상위 5개
- 가장 많이 계산된 궁합 MBTI 조합 상위 5개

- 궁합 경험 여부
- 최신순·오래된순
- 페이지당 20개, 서버 페이지네이션

초기 버전은 원본 결과 CSV 내보내기를 제공하지 않는다. 닉네임과 결과를 대량 반출하는 기능은
보존·개인정보 정책이 확정된 뒤 결정한다.

### 4.3 `/admin/results/{result_code}` 결과 상세

사용자 문의 대응을 위한 화면이다.

- 결과 코드와 생성 시각
- 닉네임
- 문항 버전·콘텐츠 버전
- MBTI, 최종 결과명, 캐릭터, 희귀도, 상단 키워드 3개
- 네 성향 축 점수
- 포장 상자와 개봉 도구
- 핵심 특징 4개
- 장난감 이야기
- 사용 방법 4개
- 주의사항 4개
- 충전 방법과 활동 3개
- 잘 맞는 친구 장난감 2개
- 궁합 파생 프로필 존재 여부
- 공개 결과 조회 횟수와 마지막 조회 시각
- 이 결과가 `mine`으로 사용된 궁합 계산 횟수
- 저장된 전체 스냅샷 JSON 접기/펼치기

현재 규칙으로 결과를 다시 계산하지 않는다. 문의 당시 사용자가 실제로 받은 **생성 시점
스냅샷**을 보여준다. 어드민 상세 조회는 공개 결과 조회 통계에 포함하지 않는다.

- 문항 버전·콘텐츠 버전 분포

#### 궁합 통계

- 궁합 계산 완료 횟수
- 궁합을 경험한 고유 `mine_result_code` 수
- 누적 궁합 경험 비율
- 결과 조회 후 궁합 전환율
- 궁합 사용 결과당 평균 계산 횟수

분석 수치는 운영과 마케팅 소재 탐색용이다. 특정 MBTI가 우월하거나 특정 조합이 심리학적으로
더 좋다는 사실로 외부에 단정하지 않는다.

## 5. 백엔드 지표 정의

| 지표 | 정의 |
|---|---|
| 생성 결과 수 | 기간 내 저장된 `assessment_results` 행 수 |
| 고유 결과 수 | `result_code` 고유 개수. 현재 제약상 생성 결과 수와 같음 |
| 공개 결과 조회 수 | `GET /api/results/{result_code}`가 200을 반환한 횟수 |
| 조회된 고유 결과 수 | 공개 결과 조회 성공 기록이 한 번 이상 있는 고유 결과 코드 수 |
| 조회 경험 결과 비율 | 공개 GET 기록이 있는 고유 결과 코드 ÷ 전체 결과 코드 |
| 궁합 계산 완료 수 | `GET /api/compatibility`가 200을 반환한 횟수 |
| 궁합 사용 결과 수 | `mine_result_code`로 궁합을 한 번 이상 완료한 고유 결과 코드 수 |
| 궁합 경험 비율 | 궁합 사용 결과 수 ÷ 전체 생성 결과 수 |
| 결과 조회 후 궁합 전환율 | 결과 조회 후 궁합을 완료한 고유 결과 코드 ÷ 조회된 고유 결과 코드 |
| 반복 궁합 사용량 | 궁합 사용 결과들의 평균 궁합 계산 횟수 |
| 평균 궁합 점수 | 성공한 궁합 계산 시점에 저장한 점수의 평균 |

궁합 경험 비율은 사용자가 요청한 핵심 백엔드 지표다. 같은 결과 코드로 여러 친구와 궁합을
계산해도 분자에서는 한 번만 센다. 기간별 단순 활동량은 `occurred_at` 기준으로 계산하고, 누적
궁합 경험 비율은 계측 배포 이후 생성된 결과만 분모에 포함한다.

결과 조회 후 궁합 전환율은 같은 `result_code`에 `result_viewed`가 먼저 기록되고, 이후 그 코드가
`mine_result_code`인 `compatibility_completed`가 한 번 이상 기록됐는지 확인한다. 호출 횟수가
아니라 고유 결과 코드로 계산한다. 로그인 사용자가 없으므로 이 수치를 정확한 사람 수가 아닌
**결과 코드 기준 전환율**로 표시한다.

공개 결과 조회 기록은 결과 페이지 로딩 방식에 영향을 받는다. 프론트가 제출 응답을 바로
사용하면 최초 결과 화면은 GET 기록에 잡히지 않고, 결과 코드로 다시 불러올 때만 기록된다.
따라서 이를 프론트 페이지뷰나 사람 단위 조회율로 해석하지 않는다.

모든 날짜 필터와 화면 표시는 `Asia/Seoul`을 기준으로 하며 DB에는 timezone-aware 시각을
저장한다.

## 6. 데이터 모델

### 6.1 기존 `assessment_results`

결과 스냅샷의 원본 역할을 그대로 유지한다. 어드민 목록을 위해 결과 필드를 별도 컬럼으로
중복 저장하지 않고 초기에는 PostgreSQL JSONB에서 읽는다. 실제 병목이 확인될 때만 읽기 모델이나
집계 테이블을 추가한다.

추가 인덱스:

- `assessment_results.created_at`

### 6.2 `backend_usage_events`

공개 프론트가 임의로 보내는 이벤트가 아니라, 백엔드가 성공 응답을 만든 시점에 직접 기록한다.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | bigint PK | 내부 ID |
| `event_name` | string | `result_viewed` 또는 `compatibility_completed` |
| `result_code` | string | 조회 결과 또는 궁합의 `mine_result_code` |
| `related_result_code` | string nullable | 궁합의 `friend_result_code` |
| `compatibility_score` | integer nullable | 궁합 완료 당시 0~100 점수 |
| `compatibility_version` | string nullable | 궁합 계산 규칙 버전 |
| `occurred_at` | timestamptz | 성공 응답 생성 시각 |

#### 기록 규칙

- `result_viewed`: 공개 결과 조회 API가 200을 반환할 때 기록
- `compatibility_completed`: 궁합 API가 200을 반환할 때 기록
- 404, 409, 422와 서버 오류는 마케팅 통계 이벤트로 저장하지 않음
- 어드민이 결과를 조회하는 행위는 기록하지 않음
- 닉네임, 전체 결과 스냅샷, 원본 답변, IP, User-Agent는 이벤트에 복사하지 않음
- 이벤트 저장 실패가 공개 결과 조회나 궁합 응답을 실패시키지 않게 함

#### 인덱스

- `(event_name, occurred_at)`
- `(result_code, event_name)`
- `(related_result_code, event_name)`

궁합 이벤트에는 계산 당시 점수와 버전을 저장해 규칙이 바뀐 뒤에도 과거 평균이 변하지 않게
한다. MBTI 조합은 두 결과 코드의 생성 시점 스냅샷을 조회해 계산한다.

### 6.3 계측 시작 설정

`PAKIT_USAGE_TRACKING_STARTED_AT`은 백엔드 사용 기록을 실제 운영에 배포한 시각이다. 과거
결과를 미사용자로 잘못 계산하지 않도록 비율 지표의 분모 하한으로 사용한다. 값이 없으면 궁합
경험 비율을 계산하지 않고 `계측 시작일 미설정`을 표시한다.

## 7. API

프론트 분석 이벤트 수집용 공개 API는 만들지 않는다.

### 어드민 API

- `GET /api/admin/dashboard`
- `GET /api/admin/results`
- `GET /api/admin/results/{result_code}`
- `GET /api/admin/analytics/results`
- `GET /api/admin/analytics/compatibility`

목록과 분석 API는 날짜 범위를 받으며 서버 페이지네이션을 사용한다. UI는 `/admin` 아래에서
이 API를 호출한다.

### 기존 API 내부 계측

- `GET /api/results/{result_code}` 성공 후 `result_viewed` 기록
- `GET /api/compatibility` 성공 후 `compatibility_completed` 기록

계측 코드는 라우터에 SQL을 직접 넣지 않고 서비스와 저장소 경계로 분리한다.

## 8. 인증·보안

어드민 페이지와 `/api/admin/*`는 인증 없이 노출하지 않는다.

초기 1인 운영의 권장안:

1. 운영 HTTPS를 전제로 한다.
2. 가능하면 배포 앞단의 접근 제어를 1차로 사용한다.
3. 백엔드는 환경변수로 설정한 단일 관리자 자격 증명을 추가 방어선으로 사용한다.
4. 관리자 자격 증명은 저장소, 문서 예시, URL, 로그에 남기지 않는다.
5. 인증 실패 응답은 결과 데이터의 존재 여부를 드러내지 않는다.
6. 어드민 응답은 `Cache-Control: no-store`를 사용한다.

MVP는 읽기 전용이므로 복잡한 관리자 계정, 역할, 권한과 감사 로그는 만들지 않는다.

## 9. 개인정보·운영 원칙

- 전체 결과 목록에서 닉네임은 기본 마스킹한다.
- 닉네임 전체값과 스냅샷 JSON은 인증된 상세 화면에서만 보여준다.
- 사용 기록에는 닉네임과 원본 답변을 저장하지 않는다.
- IP 주소, User-Agent와 브라우저 지문을 마케팅 통계용으로 저장하지 않는다.
- 사용 기록의 보존 기간과 삭제 주기는 출시 전에 확정한다.
- 닉네임과 결과 스냅샷의 보존·삭제 정책도 기존 미결정 사항으로 유지한다.
- 개인정보 처리방침과 실제 백엔드 저장 필드가 일치하는지 출시 전에 확인한다.

## 10. 구현 순서

### 1단계: 결과 관리 기반

- `assessment_results.created_at` 인덱스 마이그레이션
- 결과 목록·검색·필터 저장소
- 결과 목록과 상세 Pydantic 응답 모델
- 어드민 인증 의존성
- `/api/admin/results` API
- `/admin/results` 목록과 상세 화면

### 2단계: 백엔드 사용 기록

- `backend_usage_events` Alembic 마이그레이션
- `PAKIT_USAGE_TRACKING_STARTED_AT` 설정과 `.env.example` 문서화
- 사용 기록 저장소와 서비스
- 공개 결과 조회 성공 기록
- 궁합 계산 성공 시 점수·버전 기록
- 계측 실패가 본 응답을 막지 않는 처리

### 3단계: 대시보드·분석

- 결과 현황과 분포 집계 쿼리
- 궁합 경험 비율과 궁합 통계 쿼리
- `/api/admin/dashboard`와 분석 API
- `/admin`과 `/admin/analytics` 화면
- 계측 전 기간의 `계측 전` 처리

## 11. 완료 조건

### 결과 관리

- 결과가 0개일 때 빈 상태가 정상 표시된다.
- 최신 결과가 기본적으로 먼저 보인다.
- 결과 코드로 정확히 한 결과를 찾을 수 있다.
- 닉네임 검색과 날짜·MBTI·버전 필터가 동작한다.
- 기존 스냅샷에 MBTI나 궁합 프로필이 없어도 화면이 깨지지 않는다.
- 상세 화면은 생성 당시 저장된 스냅샷을 보여준다.
- 어드민 조회가 공개 결과 조회 수를 증가시키지 않는다.

### 백엔드 통계

- 공개 결과 조회와 궁합 API의 200 응답만 기록된다.
- 동일 결과의 반복 조회와 반복 궁합은 횟수에는 모두 반영된다.
- 같은 `mine_result_code`의 반복 궁합은 궁합 경험 비율 분자에서 한 번만 계산된다.
- 결과 조회보다 먼저 발생한 궁합 기록은 결과 조회 후 궁합 전환율 분자에서 제외된다.
- 궁합 이벤트에 당시 점수와 버전이 보존된다.
- 계측 배포 이전 기간을 0이 아니라 `계측 전`으로 구분한다.
- `Asia/Seoul` 날짜 경계를 테스트한다.

### 보안

- 인증되지 않은 요청은 어드민 HTML과 API에 접근할 수 없다.
- 목록에서 닉네임이 마스킹된다.
- 이벤트와 로그에 닉네임, 전체 답변, 비밀값이 기록되지 않는다.
- 어드민 응답에 `Cache-Control: no-store`가 적용된다.

- 원본 답변 저장과 조회
- 관리자별 역할과 권한

- 결과 삭제 UI
- 실시간 WebSocket 대시보드

## 13. 개발 전 확정할 항목

1. 운영 배포 앞단에서 사용할 접근 제어 방식
2. 백엔드 단일 관리자 자격 증명을 함께 사용할지 여부
