# 유료 AI 연인 관계 설명서 프롬프트

상태: 품질 검증용 초안. 백엔드 생성 API에 연결되어 있으며 결제 권한 검증은 아직 없다.

현재는 연인 관계만 지원한다. 공통·친구·썸 프롬프트는 사용하지 않는다.

| 파일 | 역할 |
|---|---|
| [romantic-system.md](romantic-system.md) | 모델의 역할, 해석 관점, 금지사항 |
| [romantic-user-template.md](romantic-user-template.md) | A/B 프로필 자리와 10개 출력 항목 |
| [input-contract.md](input-contract.md) | 원본 응답을 줄글 성향 프로필로 바꾸는 규칙 |

선택지별 실제 고정 문구와 조합 결과는
[프로필 문구 검수본](../../../../docs/romantic-profile-copy-review.md)에서 한 번에 확인할 수 있다.

`input-contract.md`는 개발 문서이므로 모델 호출에 넣지 않는다.

## 생성 흐름

1. DB에서 두 결과의 원본 응답 스냅샷, MBTI, 네 축 점수를 읽는다.
2. 질문지 버전에 맞는 문구 매핑과 조합 템플릿으로 각 사람의 프로필 문장을 만든다.
3. `romantic-system.md`는 API의 시스템 지시문으로 전달한다.
4. `romantic-user-template.md`에 이름, 입력받은 성별, MBTI와 프로필 문장을 채워
   사용자 메시지로 전달한다.
5. 생성 결과에는 사용한 프롬프트 버전과 프로필 문구 버전을 함께 기록한다.

질문 원문, 선택값 코드, 계산식, 기존 개인 결과 카피와 무료 궁합 문구는 LLM에 전달하지
않는다. 성향 프로필은 LLM 전처리로 만들지 않는다. 같은 원본 응답은 같은 버전에서 항상
같은 문장으로 변환되어야 한다.

기존 평가 제출과 원본 스냅샷에는 성별 필드가 없다. 무료 궁합 화면에서
`우리 관계 더 알아보기`를 누른 뒤 유료 관계 설명서 요청 전에 A와 B의 성별을 입력받는다.
이 값은 기존 평가 결과를 수정하지 않고 유료 관계 설명서 요청과 생성 스냅샷에 보존한다.
이름이나 MBTI로 성별을 추측하지 않는다.

## 비교 검수

- 개인 결과를 다시 설명하지 않고 두 사람 사이의 관계 분석에 집중하는가?
- 차이, 각자의 이유, 반복되는 상호작용, 양쪽의 조정 방법이 연결되는가?
- 2~6번 항목이 서로 다른 관계 주제를 다루는가?
- 프로필 문장을 순서대로 바꿔 쓰는 데 그치지 않는가?
- MBTI와 다른 성향 정보를 함께 사용하되 유형만으로 단정하지 않는가?
- 성별 고정관념이나 입력에 없는 관계 경험을 만들지 않는가?
- 조언이 두 사람이 실제로 사용해볼 만큼 구체적인가?
- 10번이 앞의 분석을 압축한 한 줄로 끝나는가?

검수용 근거가 필요하면 사용자 결과 생성 프롬프트에 섞지 않고 별도의 평가 프롬프트로
관리한다. 실제 생성 결과를 비교한 뒤 최종 문구 매핑, 출력 길이와 운영 버전을 확정한다.
